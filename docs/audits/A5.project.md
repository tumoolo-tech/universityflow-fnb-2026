**Who uses this:** South African learners from 16, most of them minors, and their guardians.
Treat anything that exposes a learner's data, or lets one learner act as another, as at least
**High**.

**Surfaces to attack, in order:**

1. **The agent** (`apps/web/app/api/chat`, `packages/agent`). Prompt injection through the
   learner's message, an uploaded document's text, or a tool result: can it make the agent
   state an admission fact not from `catalogue`/`admissions`, reveal another learner's data,
   call a tool outside its schema, or skip the crisis protocol? The crisis check must run
   **before** any model call, on every message.
2. **Sign-in** (`packages/db` phone OTP): PIN brute force, lockout bypass, per-number and per-IP
   limits, SMS cost abuse across many numbers (the global SMS budget), session fixation, the
   bearer token issued to the mobile app (`x-uf-client: native` on verify-pin).
3. **Consent** (`apps/web/app/api/consent`, `api/me/*`): can a minor skip guardian consent,
   re-declare their age, or can an old guardian link act on a newer request?
4. **Uploads** (`apps/web/app/api/documents`, `packages/documents`): magic-byte checks, size
   limits, signed-URL scope and expiry once S3 is connected, path traversal in the disk store.
5. **Row-level security**: one learner's rows invisible to another at the database, not just
   in the query.
6. **Headers**: CSP (per-request nonces, no script `'unsafe-inline'`), CSRF same-origin check
   on every state-changing route.

**Data residency:** student data stays in AWS af-south-1 and Vercel `cpt1`. Any new provider
that stores or processes it elsewhere is a finding unless the consent wording covers it.
